# Migration Guide: 3.5 → 4.0

This guide covers breaking changes and migration steps for upgrading from IshAstra 3.5.x to 4.0.

## Breaking Changes

### 1. Scope Gate Enforcement (Mandatory)

**Before**: Scope validation was advisory at adapter level.

**After**: Scope Gate runs at every boundary (dispatch → adapter → worker). All three layers (URL/Host, DNS/IP, Pinned Destination) are enforced by default.

**Impact**: Existing scope documents without Layer 2/3 config will reject all targets.

**Migration**:
```bash
# Update scope documents with Layer 2/3 configuration
# No command is needed: v2 scope documents already carry the Layer 2/3 fields.

# Verify scope validation passes
# Scope validation runs when the gate loads the document; no separate command exists.
```

### 2. Legacy Strix Naming Removed

**Before**: Metrics, cookies, keys, and env vars used `strix_*` prefix.

**After**: All prefixes changed to `ishastra_*`.

| Old | New |
|-----|-----|
| `STRIX_API_KEY` | `ISHASTRA_API_KEY` |
| `strix_metric_*` | `ishastra_metric_*` |
| `strix_session` cookie | `ishastra_session` cookie |
| `strix_redis_*` | `ishastra_redis_*` |

**Migration**: Update all environment files, Kubernetes secrets, and monitoring dashboards.

### 3. AI Analyst Provider Removed

**Before**: Abstract `AIAnalystProvider` interface with cloud provider implementations.

**After**: Removed entirely. Replaced by optional local AI advisor (Ollama) in `src/ishastra/core/ai.py`.

**Impact**: Code importing `ishastra.ai.AIAnalystProvider` will fail.

**Migration**: Remove AI analyst references. If AI triage needed, enable local advisor:
```bash
ISHASTRA_AI_ENABLED=true
ISHASTRA_AI_OLLAMA_URL=http://localhost:11434
ISHASTRA_AI_MODEL=llama3.1:8b
```

### 4. Adapter Interface v2 Required

**Before**: v1 adapter interface with sync `run()` method.

**After**: v2 interface with async `run_async()` and mandatory Scope Gate re-check.

**Migration**:
```bash
# Migrate custom adapters
# No automatic migration: implement Adapter.available()/assess() (see adapter_base.py).

# Update imports
# OLD: from ishastra.adapters import MyAdapter
# NEW: from ishastra.adapters.base import AdapterBase
```

### 5. Queue Mode Changes

**Before**: `redis` and `inprocess` modes.

**After**: `in-process`, `redis-streams`, `k8s-jobs`, `sqlite` modes.

**Migration**: Update `ISHASTRA_QUEUE_MODE` in environment:
```bash
# Old
ISHASTRA_QUEUE_MODE=redis

# New (choose one)
ISHASTRA_QUEUE_MODE=redis-streams
ISHASTRA_QUEUE_MODE=k8s-jobs
ISHASTRA_QUEUE_MODE=sqlite
ISHASTRA_QUEUE_MODE=in-process
```

### 6. Database Schema Migrations

New tables added:
- `capability_tokens` (capability JWT storage)
- `capability_revocations` (revocation list)
- `evidence_signatures` (artifact signatures)
- `organizations`, `teams`, `memberships` (Org v2)

Run migrations:
```bash
# No separate migration command: the store applies the schema chain at startup.
```

### 7. Rules of Engagement (RoE) Extended

New fields in engagement policy:
```yaml
testing_hours:
  start: "09:00"
  end: "18:00"
  timezone: "UTC"
rate_limit_rps: 10.0
prohibited_techniques:
  - "sql_injection"
  - "dos"
required_notifications:
  - email: "security@example.com"
    events: ["assessment_started", "critical_finding"]
data_handling:
  retention_days: 90
  encryption_required: true
```

### 8. High-Risk Authorization

New explicit flags:
- Engagement: `high_risk_allowed: true`
- Job config: `high_risk: true`

Without these, high-risk techniques (SQLi, auth bypass, DoS) are rejected at dispatch.

### 9. CLI Command Changes

| Old Command | New Command |
|-------------|-------------|
| `ishastra worker` | `ishastra worker gateway` for a dedicated Redis Streams worker |

### 10. Deployment Defaults

**Before**: PostgreSQL required.

**After**: SQLite default, PostgreSQL experimental.

```yaml
# docker-compose.yml now uses SQLite by default
# For PostgreSQL:
ISHASTRA_DATABASE_URL=postgresql://user:pass@db:5432/ishastra
ISHASTRA_QUEUE_MODE=redis-streams
```

## Migration Checklist

- [ ] Update all `STRIX_*` env vars to `ISHASTRA_*`
- [ ] Run `# No separate migration command: the store applies the schema chain at startup.`
- [ ] Confirm existing scope documents use the v2 schema
- [ ] Update custom adapters to v2 interface
- [ ] Set `ISHASTRA_QUEUE_MODE` to new value
- [ ] Configure RoE with `rate_limit_rps` and `high_risk_allowed`
- [ ] Update monitoring dashboards for new metric prefixes
- [ ] Test assessment end-to-end in staging
- [ ] Verify evidence signing works (`ishastra evidence verify`)
- [ ] Enable local AI advisor if needed (optional)

## Rollback Plan

If issues arise:
```bash
# 1. Revert database
# Schema is forward-only: restore the pre-upgrade database backup.

# 2. Restore 3.5.x images
docker-compose pull ishastra:v3.5.0

# 3. Restore env vars (STRIX_* prefix)

# 4. Restore scope documents (Layer 1 only)
```
